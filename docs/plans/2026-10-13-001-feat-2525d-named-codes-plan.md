# feat: Named MIL-STD-2525D entity and modifier codes

## Overview

Let callers write names from the standard instead of raw digit strings, scoped
by symbol set:

```ts
import { Air } from "milsymbol-sidc/2525d";

new Sidc({ standard: Standard.MilStd2525, strict: true })
  .version(Version.MilStd2525D)
  .identity(StandardIdentity.Friend) //       "3"
  .symbolSet(Air) //                          "01"
  .entity(Air.Entity.Civilian.FixedWing) //    "120100"
  .modifier1(Air.Modifier1.Passenger) //       "09"
  .modifier2(Air.Modifier2.Heavy) //           "01"
  .toString(); // "10030100001201000901"
```

Names are generated from Esri's Joint Military Symbology Markup Language
(JMSML), an Apache-2.0 XML encoding of MIL-STD-2525D / APP-6(D), into an
optional `milsymbol-sidc/2525d` subpath. Raw strings keep working and default
output does not change.

Implemented with the recommended answers to the open questions below
(adopt-when-`00` plus throw on mismatch; control-measure names included;
`milsymbol-sidc/2525d`; structured `.entity({ entity, type, subtype })` shipped
together). Deviations: the "subtype without type" warning floated earlier was
dropped because it would make currently valid codes report problems.

---

## Requirements Trace

- R1. Hierarchical entity names (entity › type › subtype) and flat modifier 1 /
  modifier 2 names, all scoped to their symbol set.
- R2. Every named node exposes its exact code and the standard's label, so UIs
  can display names (for example the sample page's breakdown table).
- R3. Purely additive: existing string setters, output, snapshots, warnings,
  and problem codes are unchanged; the core entry point gains no data.
- R4. Reproducible: generated from a pinned JMSML commit, regenerated by a
  script, and checked for staleness in CI like `catalogs.generated.ts`.
- R5. Honest edition labelling: the subpath is named for 2525D; nothing
  implies edition E coverage.
- R6. Reverse lookup: turn an existing SIDC back into names.

---

## Scope Boundaries

- MIL-STD-2525D names only. Edition E (and 2525D Change 1 renames) need a
  different source and would be a separate subpath (for example `/2525e`).
- METOC symbol sets 45/46/47 are excluded: milsymbol cannot render them and the
  core `SymbolSet` enum does not list them.
- No change to `toString()` validation: names are a convenience, not a new
  membership check (the catalogs subpath remains the renderability answer).
- No runtime network access, and no new runtime dependency.

## Context and Research

Measured against JMSML `dev` at commit
`094e7647f0bdd001e42fd2a73ba802c995af20aa` (repository archived; last push
2024-09-19; Apache-2.0) and the milsymbol 3.0.4 catalog.

### What JMSML provides

- One XML file per symbol set (23 sets) with `ID`, `Label`, optional
  `LabelAlias`, and two-digit codes at every level: 142 entities, 935 entity
  types, 1,004 entity subtypes, 628 modifiers (sector 1 and sector 2).
- Four "special" subtypes (land unit `95`–`98`, e.g. headquarters element)
  that apply to any entity/type rather than one parent.
- Edition detail is almost absent: only three elements carry
  `Standard="MILSTD_2525"`; there is no Change 1 or APP-6(D)-only marking.
- Example (Air): entity `12` Civilian › type `01` Fixed Wing; modifier 1 `09`
  Passenger, `37` Hijacking; modifier 2 `01` Heavy.

### Fit with milsymbol (excluding METOC)

| | Count |
| --- | --- |
| JMSML entity nodes | 1,666 |
| …rendered by milsymbol | 1,296 |
| milsymbol catalog entity codes | 1,376 |
| …with a JMSML name | 1,296 |
| JMSML modifiers / rendered by milsymbol | 628 / 603 |

- Most unrendered JMSML entities are line/area control measures (set 25:
  603 named, 252 rendered); milsymbol draws point symbols only.
- 80 milsymbol codes have no 2525D name (e.g. 22 in cyberspace); these are
  likely edition E additions, consistent with R5.
- Every set's `000000` ("Unspecified") and modifier `00` ("Not Applicable")
  are named but are not catalog entries; they are valid "none" values.

### Naming

- PascalCase from `Label` gives clean identifiers (`FixedWing`,
  `AttackStrike`, `Passenger`) with a single sibling collision in all data
  (set 25, "Navigational Reference Point").
- 40 of 2,294 identifiers exceed 40 characters, e.g. the Air UAV type
  (`UnmannedAircraftUAUnmannedAerialVehicleUAV…RPV`). JMSML's `LabelAlias`
  ("Unmanned Aircraft (UA, UAV, UAS, RPV)") shortens many; the rest need a
  small override table.

## Key Technical Decisions

### Node shape

Every named item is a frozen object, never a bare string, so adding a child in
a future data update cannot turn a leaf into a branch and break callers:

```ts
Air.Entity.Civilian.FixedWing
// { code: "120100", label: "Fixed Wing", symbolSet: "01",
//   ...child subtypes as further nodes }
Air.Modifier1.Passenger
// { code: "09", label: "Passenger", symbolSet: "01" }
Air // { code: "01", label: "Air", Entity: {...}, Modifier1: {...}, Modifier2: {...} }
```

`code` is typed as a string literal (`as const`), so editors show the digits.
Generated child names that would clash with `code`, `label`, or `symbolSet`
get a suffix.

### Setters accept nodes (additive overload)

`symbolSet()`, `entity()`, `modifier1()`, `modifier2()` accept either the
existing string or any `{ code: string }` node; the node's `code` goes through
the same validation as a string. No new stored state: snapshots and
`toObject()` are unchanged.

### Symbol-set safety

A node carries the symbol set it belongs to. Passing `Air.Modifier1.Passenger`
to a land-unit builder is a real mistake (`09` means something else there).
Proposed rule, checked in the setter:

- builder symbol set equals the node's: accept;
- builder symbol set is still the default `00` (Unknown): adopt the node's
  symbol set, so `.entity(Air.Entity…)` works before `.symbolSet(Air)`;
- otherwise: throw `SidcValidationError`
  (`Air modifier 1 "Passenger" used on symbol set 10.`).

Changing `symbolSet()` later is not re-checked (no stored provenance); that is
documented, and `describe2525d()` (below) makes the result inspectable.

### Reverse lookup

`describe2525d(sidc: string | Sidc)` returns the names for a code, with
`undefined` where JMSML has none:

```ts
describe2525d("10030100001201000901");
// { symbolSet: { code: "01", label: "Air" },
//   entity: [{ code: "12", label: "Civilian" }, { code: "01", label: "Fixed Wing" }],
//   modifier1: { code: "09", label: "Passenger" },
//   modifier2: { code: "01", label: "Heavy" } }
```

### Data pipeline (two steps)

1. `scripts/import-jmsml.mjs` (rare, needs network): download the pinned
   commit's XML, normalize to `data/jmsml-2525d.json` (sets, nodes, codes,
   labels, aliases), and commit it. Parsing uses a dev-only XML parser.
2. `scripts/generate-names.mjs` (offline, CI-checked): read the JSON plus
   `scripts/name-overrides.json`, write `src/names-2525d.generated.ts`, format
   it. CI runs it and fails on a diff, like `generate:catalogs`.

The generated file carries the JMSML commit, the Apache-2.0 notice, and
attribution; `NOTICE`/README credit Esri's JMSML.

### Packaging

- Subpath export `milsymbol-sidc/2525d` → `dist/src/names-2525d.js`, never
  imported by the main entry point.
- One named export per symbol set (`Air`, `LandUnit`, …) so bundlers keep only
  the sets an app imports. Export names follow the core `SymbolSet` enum
  (`LandUnit`, not JMSML's `LandUnits`).

## Implementation Units

1. **Import** — `import-jmsml.mjs`, `data/jmsml-2525d.json`, special-subtype
   handling, METOC exclusion.
2. **Generate** — naming rules (Label → alias when >40 chars → override),
   collision and reserved-name handling, literal-typed frozen nodes,
   `npm run generate:names`, CI staleness check.
3. **Builder overloads** — node-or-string setters with the symbol-set rule;
   unchanged string behavior and messages.
4. **`describe2525d()`** — reverse lookup in the subpath.
5. **Tests** — every node's code is well-formed and unique per parent; codes
   that milsymbol renders match the catalog; overload/mismatch behavior;
   README examples executed by the existing harness.
6. **Docs** — README section, CHANGELOG, and the civil-airliner sample using
   `Air.Modifier1.Passenger` etc. with the breakdown table driven by
   `describe2525d()`.

## System-Wide Impact and Risks

- **Package size**: whole file is an estimated low hundreds of kB unminified;
  per-set exports keep real bundles small. Measure in unit 2.
- **Source staleness**: JMSML is archived. Names are frozen at 2525D; this is
  stated, not hidden.
- **Label quirks**: inconsistent punctuation in source labels (e.g. ATF agency
  variants) produce odd identifiers; overrides fix the visible ones.
- **APP-6(D)**: JMSML covers both families, but without per-standard marking
  the subpath is presented as 2525D only.

## Open Questions

1. Symbol-set rule: adopt-when-`00` plus throw on mismatch (proposed), or
   always throw / never check?
2. Include line/area control measures that milsymbol cannot draw (proposed:
   yes, names are standard data), or only renderable codes?
3. Subpath name: `milsymbol-sidc/2525d` (proposed) or `milsymbol-sidc/names`?
4. Ship the structured `.entity({ entity, type, subtype })` form at the same
   time? It is the natural home for the four special land-unit subtypes.
